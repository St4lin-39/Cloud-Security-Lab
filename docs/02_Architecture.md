# Cloud Security Lab

# System Architecture

## 1. Architecture Overview

Cloud Security Lab was designed following a modular architecture based on the **Separation of Concerns** principle, where every component performs a single, clearly defined responsibility within the security event processing pipeline.

The primary objective of this architecture is to facilitate scalability, maintainability, extensibility, and future integration with additional security capabilities without requiring modifications to the system's core components.

Rather than implementing a monolithic solution, Cloud Security Lab separates event generation, threat detection, alert management, alert correlation, persistence, and visualization into independent modules.

This architecture resembles the internal processing workflow commonly found in modern Security Information and Event Management (SIEM) platforms.

---

# 2. High-Level Architecture

The overall processing workflow is illustrated below.

```text
Attack Runner
      │
      ▼
Event Generator
      │
      ▼
PostgreSQL (Events)
      │
      ▼
Detection Engine
      │
      ▼
Alert Manager
      │
      ▼
Alert Enrichment
      │
      ▼
Correlation Engine
      │
      ▼
PostgreSQL (Alerts)
      │
      ▼
Power BI
```

Each component consumes the output generated by the previous layer, processes the information according to its responsibility, and forwards the result to the next module.

This sequential architecture simplifies maintenance while allowing every component to evolve independently.

---

# 3. Architecture Principles

The system was designed following several software engineering principles that promote long-term maintainability.

- Separation of Concerns
- Single Responsibility Principle
- Low Coupling
- High Cohesion
- Repository Pattern
- Modular Design
- Extensibility
- Scalability
- Code Reusability
- Maintainability

These principles make it possible to introduce new attack simulations, detection modules, alert types, correlation rules, dashboards, and cloud integrations without redesigning the existing architecture.

# 4. Components

## 4.1 Attack Runner

The Attack Runner represents the entry point of the simulation environment.

Its responsibility is to execute predefined attack scenarios that generate realistic security events for later analysis.

The current implementation includes simulations for:

- Brute Force
- Resource Enumeration
- Credential Stuffing
- Password Spraying

Each attack scenario generates multiple events that are immediately forwarded to the Event Generator.

The Attack Runner contains no detection logic and is exclusively responsible for orchestrating attack simulations.

---

## 4.2 Event Generator

The Event Generator creates individual security events representing user activity inside the simulated environment.

Each generated event includes information such as:

- Username
- Source IP Address
- Event Type
- Target Resource
- Password Attempt (when applicable)
- Timestamp

Once generated, events are persisted into PostgreSQL before being processed by the Detection Engine.

The Event Generator performs no threat analysis, preserving a strict separation between event generation and detection.

---

## 4.3 Database Layer

PostgreSQL serves as the primary persistence layer for the platform.

The current implementation contains two main entities.

### Events

Stores every security event generated during attack simulations.

This table represents the complete activity history of the system.

### Alerts

Stores only security alerts generated by the Detection Engine and Correlation Engine.

Unlike raw events, alerts contain enriched contextual information including:

- Alert Type
- Severity
- Operational Status
- Description
- Recommendation
- Username (when applicable)
- Source IP
- Attempts Volume
- Creation Timestamp

Separating events from alerts preserves the original activity history while keeping processed security information isolated for investigation and reporting.

---

## 4.4 Detection Engine

The Detection Engine is the analytical core of Cloud Security Lab.

Every incoming event is evaluated against all registered detection modules through the Detection Registry.

The current implementation includes four independent detectors:

- Brute Force Detection
- Resource Enumeration Detection
- Credential Stuffing Detection
- Password Spraying Detection

Each detector operates independently and follows a rule-based detection strategy.

This architecture allows new detection modules to be incorporated simply by registering them in the Detection Registry without modifying the Detection Engine itself.

---

## 4.5 Alert Manager

The Alert Manager is responsible for managing every alert generated by the Detection Engine.

Its responsibilities include:

- Preventing duplicate alerts through configurable suppression windows.
- Reducing operational noise.
- Enriching alerts with contextual metadata before persistence.

Each alert is automatically enriched with:

- Severity
- Operational Status
- Human-readable Description
- Analyst Recommendation

This enrichment transforms raw detections into actionable security information suitable for incident investigation and dashboard visualization.

---

## 4.6 Alert Enrichment

Alert enrichment is implemented through a centralized metadata configuration.

Rather than hardcoding descriptive information inside every detector, contextual information is maintained independently through the Alert Metadata configuration.

This design decouples detection logic from presentation logic while improving maintainability.

Every generated alert automatically receives:

- Severity Classification
- Operational Status
- Description
- Recommendation

Future versions will extend this enrichment with:

- MITRE ATT&CK Techniques
- Confidence Scores
- Risk Scores
- Threat Categories

---

## 4.7 Correlation Engine

The Correlation Engine represents the highest analytical layer of the platform.

Instead of analyzing raw events, it analyzes previously generated alerts to identify more complex attack patterns.

The current implementation includes one correlation rule:

### Multi-Stage Attack

The engine correlates:

- Brute Force
- Resource Enumeration
- Credential Stuffing

generated from the same source IP within a configurable time window.

When all required alerts are present, a higher-severity **Multi-Stage Attack** alert is generated.

This approach closely resembles correlation strategies implemented by enterprise SIEM platforms.

---

## 4.8 Power BI

Power BI represents the visualization layer of Cloud Security Lab.

Its purpose is to transform security events and alerts into interactive dashboards that facilitate investigation and decision-making.

Current dashboards include:

- Executive Overview
- IP Analysis
- User Analysis
- Resource Analysis
- Incident Investigation

Future versions will include dashboards focused on:

- MITRE ATT&CK
- Threat Hunting
- IOC Analysis
- Risk Scoring

# 5. Layer Responsibilities

| Layer | Responsibility |
|---------|----------------|
| Attack Runner | Execute attack simulations |
| Event Generator | Generate security events |
| PostgreSQL | Persist events and alerts |
| Detection Engine | Execute rule-based detections |
| Alert Manager | Suppress duplicate alerts |
| Alert Enrichment | Add contextual metadata |
| Correlation Engine | Detect multi-stage attacks |
| Power BI | Visualize security information |

This strict separation allows each module to evolve independently while minimizing coupling between components.

# 7. Architectural Decisions

Several architectural decisions were made during development to maximize maintainability and extensibility.

The most significant include:

- Repository Pattern used to decouple business logic from data access.
- Detection Engine implemented independently from event generation.
- Detection Pipeline introduced as an orchestration layer between event generation and threat detection.
- Detection Registry used to dynamically execute independent detection modules.
- Alert Metadata centralized to decouple contextual information from detection logic.
- Alert Suppression implemented to reduce operational noise.
- Correlation Engine separated from individual detectors.
- Power BI adopted exclusively as the visualization layer.

Together, these decisions provide a clean and extensible foundation for future platform evolution.

Cloud Security Lab currently provides a fully functional modular detection platform capable of:

- Simulating multiple cyberattack scenarios.
- Generating realistic security events.
- Detecting malicious behavior through rule-based analytics.
- Enriching alerts with contextual metadata.
- Suppressing duplicate alerts.
- Correlating multiple detections into higher-level security incidents.
- Persisting information inside PostgreSQL.
- Visualizing security information through Power BI dashboards.

The current implementation establishes a robust architectural foundation for future versions that will incorporate advanced threat hunting capabilities, cloud security telemetry, behavioral analytics, MITRE ATT&CK mapping, and automated incident response.
