# Cloud Security Lab

# System Architecture

## 1. Architecture Overview

Cloud Security Lab was designed following a modular architecture based on the **Separation of Concerns** principle, where each component performs a specific function within the security event processing pipeline.

The primary objective of this architecture is to facilitate scalability, maintainability, and the integration of new capabilities without affecting the existing system.

The platform follows a sequential processing workflow that transforms security events into meaningful information for analysis.

---

# 2. High-Level Architecture

The overall system workflow is as follows:

```
Attack Runner
      │
      ▼
Event Generator
      │
      ▼
 PostgreSQL (Events)
      │
      ▼
Detection Engine
      │
      ▼
Alert Manager
      │
      ▼
Correlation Engine
      │
      ▼
PostgreSQL (Alerts)
      │
      ▼
Power BI
```

Each component receives information from the previous one, processes it, and passes the result to the next module.

---

# 3. Architecture Principles

The architecture was designed based on the following principles:

* Separation of concerns.
* Low coupling between components.
* High cohesion within each module.
* Code reusability.
* Scalability.
* Maintainability.
* Readiness for future integrations.

These principles make it possible to add new detection rules, new attack types, and new analysis engines without modifying the core architecture of the system.

---

# 4. Components

## 4.1 Attack Runner

The Attack Runner represents the entry point for attack simulations.

Its responsibility is to execute predefined attack scenarios.

It currently implements simulations for:

* Brute Force
* Resource Enumeration
* Credential Stuffing

Each simulation generates multiple events that are subsequently analyzed by the system.

---

## 4.2 Event Generator

The Event Generator is responsible for creating individual security events.

Each event represents an action performed by a user or an IP address within the system.

Its sole responsibility is to generate valid events and store them in the database.

This module performs no detection logic.

---

## 4.3 Database Layer

The PostgreSQL database serves as the primary storage layer of the system.

The current implementation contains two main entities:

**Events**

Stores all activity generated during attack simulations.

**Alerts**

Stores only the alerts generated by the Detection Engine.

Separating events from alerts preserves the complete activity history while keeping raw data separate from processed security information.

---

## 4.4 Detection Engine

The Detection Engine is the core component of the system.

Its responsibility is to execute all available detection rules for every incoming event.

It currently implements three independent detectors:

* Brute Force Detection
* Resource Enumeration Detection
* Credential Stuffing Detection

Each detector operates completely independently.

This design allows new detection rules to be added without modifying the existing ones.

---

## 4.5 Alert Manager

Not every detected alert should be stored.

During repetitive attacks, it is common to generate multiple identical alerts that only increase operational noise.

The Alert Manager implements alert suppression mechanisms using configurable time windows.

If an equivalent alert has already been recorded recently for the same IP address, the new alert is discarded.

This mechanism significantly reduces redundant information.

---

## 4.6 Correlation Engine

The Correlation Engine represents the highest analytical layer within the architecture.

Its purpose is to analyze previously generated alerts in order to identify more complex attack patterns.

It currently implements a **Multi-Stage Attack** correlation, where different alert types are combined to generate a higher-severity alert.

This approach provides a simplified representation of how enterprise SIEM platforms perform alert correlation.

---

## 4.7 Power BI

Power BI represents the visualization layer of the system.

Its purpose is to transform the events and alerts stored in PostgreSQL into interactive dashboards that facilitate security analysis.

The project currently includes dashboards for:

* Executive Overview
* IP Analysis
* User Analysis
* Resource Analysis
* Incident Investigation

---

# 5. Layer Responsibilities

Each layer has clearly defined responsibilities.

| Layer              | Responsibility                         |
| ------------------ | -------------------------------------- |
| Attack Runner      | Execute attack scenarios               |
| Event Generator    | Generate events                        |
| Database           | Persist information                    |
| Detection Engine   | Detect threats                         |
| Alert Manager      | Reduce noise through alert suppression |
| Correlation Engine | Correlate multiple alerts              |
| Power BI           | Visualize information                  |

This separation allows each component to evolve independently.

# 6. Scalability

The architecture was designed with future versions in mind.

Planned capabilities include:

* Additional detection rules.
* MITRE ATT&CK Mapping.
* Threat Hunting.
* User and Entity Behavior Analytics (UEBA).
* Machine Learning.
* SOAR.
* Cloud integrations.
* Windows Event Logs integration.
* Syslog integration.

Adding these capabilities will not require changes to the overall architecture, only extensions to the corresponding components.

---

# 7. Architectural Decisions

Several architectural decisions were made during development to maintain a clean and maintainable design.

The most relevant include:

* Using the Repository pattern to decouple business logic from data access.
* Implementing a Detection Engine independent from the event generation layer.
* Separating detection from correlation.
* Implementing alert suppression to reduce operational noise.
* Using Power BI exclusively as the visualization layer.
* Detection Pipeline used as an orchestration layer between event generation and threat detection.
* Independent detection modules registered through a Detection Registry to facilitate future extensibility.

These decisions help maintain a modular architecture prepared for future expansion.

---

# 8. Current Architecture Status

The implemented architecture corresponds to the first functional version of Cloud Security Lab.

Version 1.0 provides a solid foundation for continuously incorporating capabilities commonly found in modern security monitoring and analysis platforms without requiring a redesign of the system's core components.
