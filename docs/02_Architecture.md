# Cloud Security Lab

# System Architecture

## 1. Architecture Overview

Cloud Security Lab was designed following a modular architecture based on the **Separation of Concerns** principle, where every component performs a single responsibility within the security event processing pipeline.

The objective of the architecture is to provide a clean, scalable, and extensible foundation that resembles the internal workflow of modern Security Information and Event Management (SIEM) platforms while remaining easy to understand and maintain.

Instead of directly generating alerts from events, the platform progressively enriches each detection with contextual information before storing it for analysis.

---

# 2. High-Level Architecture

The complete processing workflow is illustrated below.

```text
Attack Runner
      │
      ▼
Event Generator
      │
      ▼
PostgreSQL (Events)
      │
      ▼
Detection Engine
      │
      ▼
Alert Factory
      │
      ▼
Confidence Engine
      │
      ▼
Risk Engine
      │
      ▼
Alert Manager
      │
      ▼
Correlation Engine
      │
      ▼
PostgreSQL (Alerts)
      │
      ▼

```

Each component receives information from the previous layer, performs a specific task, and passes the enriched result to the next stage.

---

# 3. Architecture Principles

The architecture was designed according to the following engineering principles:

- Separation of Concerns
- Single Responsibility Principle
- Low Coupling
- High Cohesion
- Code Reusability
- Scalability
- Maintainability
- Extensibility

These principles allow new attack simulations, detection rules, enrichment engines, and visualization capabilities to be incorporated without modifying the existing architecture.

# 4. Components

## 4.1 Attack Runner

The Attack Runner represents the entry point for attack simulations.

Its responsibility is to execute predefined attack scenarios that emulate realistic attacker behavior.

Current simulations include:

- Brute Force
- Resource Enumeration
- Credential Stuffing
- Password Spraying

The Attack Runner generates events only; it performs no detection logic.

---

## 4.2 Event Generator

The Event Generator creates individual security events representing actions performed by users or IP addresses.

Each generated event is immediately stored in PostgreSQL and becomes available for detection.

Responsibilities:

- Create standardized events.
- Persist events.
- Maintain event consistency.

---

## 4.3 Database Layer

PostgreSQL serves as the persistence layer.

The database currently contains two primary entities.

### Events

Stores every simulated security event generated during attack execution.

### Alerts

Stores only validated security alerts after detection, enrichment, suppression, and correlation.

Separating raw events from processed alerts preserves the complete activity history while simplifying security analysis.

---

## 4.4 Detection Engine

The Detection Engine represents the analytical core of Cloud Security Lab.

Its responsibility is to execute every registered detection rule for each incoming event.

Current detectors include:

- Brute Force Detection
- Resource Enumeration Detection
- Credential Stuffing Detection
- Password Spraying Detection

Each detector operates independently through the Detection Registry, allowing future rules to be incorporated without modifying existing implementations.

---

## 4.5 Alert Factory

The Alert Factory standardizes the creation of alerts.

Instead of allowing each detector to manually populate alert attributes, the Alert Factory constructs a unified alert object using centralized metadata.

This guarantees consistency across every alert generated by the platform.

Responsibilities:

- Standardize alert creation.
- Retrieve alert metadata.
- Reduce duplicated code.
- Simplify maintenance.

---

## 4.6 Confidence Engine

The Confidence Engine evaluates the strength of the evidence supporting a detection.

Unlike severity, confidence is calculated dynamically based on the observed behavior.

Examples include:

- Failed authentication attempts.
- Number of affected accounts.
- Number of accessed resources.

The resulting Confidence Score ranges from 0 to 100.

---

## 4.7 Risk Engine

The Risk Engine calculates a Risk Score that helps prioritize security incidents.

The score combines:

- Alert Severity
- Detection Confidence

This provides a numerical representation of the operational priority associated with each alert.

---

## 4.8 Alert Manager

Repeated attack activity can generate excessive numbers of identical alerts.

The Alert Manager implements alert suppression mechanisms using configurable cooldown windows.

If an equivalent alert already exists for the same source IP within the configured interval, the new alert is discarded.

This significantly reduces operational noise.

---

## 4.9 Correlation Engine

The Correlation Engine represents the highest analytical layer of the platform.

Rather than analyzing individual events, it analyzes previously generated alerts.

The current implementation identifies a Multi-Stage Attack whenever the same source IP produces:

- Brute Force
- Resource Enumeration
- Credential Stuffing

within the configured correlation window.

This simplified correlation model resembles the workflow followed by enterprise SIEM platforms.

---

## 4.10 Power BI

Power BI represents the visualization layer.

Its responsibility is to transform stored events and alerts into interactive dashboards that facilitate investigation and decision-making.

Current dashboards include:

- Executive Overview
- Network Activity
- User Analysis
- Resource Analysis
- Attack Timeline
- Attack Investigation

# 5. Layer Responsibilities

| Layer | Responsibility |
|---------|----------------|
| Attack Runner | Execute attack simulations |
| Event Generator | Generate and persist security events |
| PostgreSQL (Events) | Store raw events |
| Detection Engine | Execute detection rules |
| Alert Factory | Build standardized alerts |
| Confidence Engine | Calculate detection confidence |
| Risk Engine | Calculate alert priority |
| Alert Manager | Suppress duplicated alerts |
| Correlation Engine | Detect multi-stage attacks |
| PostgreSQL (Alerts) | Store enriched alerts |
| Power BI | Visualize security information |

Each layer is isolated from the others, allowing independent evolution and simplifying future maintenance.

The architecture was intentionally designed to support incremental evolution.

Future capabilities include:

- Incident Classification
- Asset Criticality

- MITRE ATT&CK Expansion
- User and Entity Behavior Analytics (UEBA)
- Machine Learning
- SOAR Integration
- Windows Event Logs
- Syslog Integration
- AWS CloudTrail
- Azure Activity Logs

These additions can be implemented as new independent modules without requiring modifications to the existing architecture.

---

# 7. Architectural Decisions

Several architectural decisions were adopted to maintain a professional and maintainable codebase.

The most relevant include:

- Repository Pattern for data access.
- Detection Engine independent from event generation.
- Detection Registry for modular detector registration.
- Detection Pipeline as an orchestration layer.
- Alert Factory for standardized alert creation.
- Confidence Engine for dynamic confidence calculation.
- Risk Engine for incident prioritization.
- Separation between detection and correlation.
- Alert suppression through cooldown windows.
- Power BI as an isolated visualization layer.

Together, these decisions provide a modular architecture closely aligned with the internal workflow of enterprise SIEM platforms.

# 8. Current Architecture Status

The current implementation corresponds to **Cloud Security Lab v1.0**.

Version 1.0 establishes a complete modular foundation capable of:

- Simulating realistic attack scenarios.
- Detecting malicious behaviors.
- Enriching alerts with contextual information.
- Prioritizing incidents.
- Correlating multiple attack techniques.
- Visualizing security information through interactive dashboards.

This architecture provides a scalable foundation for progressively incorporating behavioral analytics, cloud telemetry, machine learning, and automated incident response in future versions.
