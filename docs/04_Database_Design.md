# Cloud Security Lab

# Database Design

## 1. Introduction

The database is the component responsible for storing all information generated during the execution of Cloud Security Lab.

Its design aims to maintain a clear separation between the events produced by the system and the alerts generated by the detection process, preserving both the original information and the analysis results produced by the Detection Engine.

Version 1.0 uses PostgreSQL as the database management system and SQLAlchemy as the Object-Relational Mapper (ORM) to abstract persistence operations.

---

# 2. Design Philosophy

The data model was designed based on the following principles:

* Data normalization.
* Separation between raw data and processed data.
* Support for analytical queries.
* Scalability.
* Compatibility with Business Intelligence tools.

Each entity represents a different stage within the security processing workflow.

---

# 3. Database Model

The system currently consists of two primary entities:

```text id="7zhhgd"
Events
    │
    ▼
Detection Engine
    │
    ▼
Alerts
```

Events represent recorded system activity.

Alerts represent the results of the analysis performed on those events.

---

# 4. Events Table

The **Events** table stores every event generated by the system.

Each record represents an individual action performed by a user or an IP address.

Examples include:

* Authentication attempts.
* Resource access.
* Events generated during attack simulations.

Events are never modified once they have been stored.

This ensures that the complete event history is preserved for future analysis.

### Stored Information

* Identifier.
* Username.
* IP address.
* Event type.
* Accessed resource.
* Timestamp.

---

# 5. Alerts Table

The **Alerts** table stores only the events that have been classified as suspicious by the Detection Engine.

Each alert represents a conclusion obtained after analyzing one or more events.

Alerts contain summarized information about the detected behavior.

### Stored Information

* Identifier.
* Alert type.
* Username.
* IP address.
* Attempt volume.
* Timestamp.

---

# 6. Why Separate Events and Alerts?

One of the fundamental principles of the project is to keep the original data separate from the results of the analysis process.

This decision provides several advantages.

## Historical Preservation

All events remain available even when they do not generate any alerts.

## Reprocessing

New detection rules can be executed against historical events without the need to regenerate the original data.

## Auditing

It is possible to determine exactly which events led to the generation of a specific alert.

## Scalability

New detection engines can be incorporated without modifying the core data model.

---

# 7. Repository Layer

Database access is completely decoupled through the Repository pattern.

Each entity has its own repository responsible exclusively for persistence operations.

The current implementation includes:

* Event Repository
* Alert Repository

This approach prevents business logic from interacting directly with SQLAlchemy.

---

# 8. Database Workflow

The information flow within the database can be summarized as follows:

```text id="dr34gs"
Attack Runner

↓

Event Generator

↓

Events Table

↓

Detection Engine

↓

Alerts Table

↓

Power BI
```

Information flows in only one direction.

Previously stored events are never modified.

---

# 9. Analytical Queries

The data model was designed to facilitate analytical queries that are later consumed by Power BI.

Examples include:

* Events by user.
* Events by IP address.
* Events by resource.
* Alerts by type.
* Alerts by user.
* Alerts by IP address.
* Attack correlation.
* Incident timeline analysis.

These queries make it possible to build dashboards without modifying the underlying data model.

---

# 10. Current Limitations

Version 1.0 intentionally maintains a simple data model.

The following entities are not currently implemented:

* Incidents.
* Assets.
* Devices.
* Risk.
* Severity.
* System users.
* Investigation cases.
* Threat Intelligence.

These entities can be incorporated in future versions without affecting the existing architecture.

---

# 11. Future Evolution

Future versions will extend the data model by incorporating new entities commonly found in enterprise SIEM platforms.

These include:

* Risk Score.
* Severity.
* Incident Management.
* MITRE ATT&CK Mapping.
* Threat Intelligence.
* Asset Inventory.
* User Profiles.
* Geolocation.
* Historical Correlation.

These enhancements will significantly increase the analytical capabilities of the system while preserving the core processing workflow implemented in version 1.0.
