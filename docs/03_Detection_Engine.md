# Cloud Security Lab

# Detection Engine

## 1. Introduction

The Detection Engine is the analytical core of Cloud Security Lab.

Its responsibility is to evaluate every event generated by the system, apply a predefined set of detection rules, and determine whether the event represents potentially malicious behavior.

Unlike solutions based on artificial intelligence or statistical models, version 1.0 implements a fully rule-based detection engine, providing a transparent understanding of the decision-making process while facilitating the integration of new capabilities in future versions.

---

# 2. Detection Philosophy

Cloud Security Lab adopts a rule-based detection approach for the following reasons:

* Simplicity of implementation.
* Ease of explaining every decision made by the system.
* Deterministic results.
* Low computational cost.
* High maintainability.
* A solid foundation for incorporating more advanced techniques in future versions.

Each rule represents a behavior considered suspicious within the context of the laboratory.

When a rule is triggered, the engine generates an alert that is subsequently processed by the alert suppression and correlation mechanisms.

---

# 3. Detection Pipeline

The event processing workflow follows the sequence below:

```text
Event

↓

Detection Engine

↓

Detection Rules

↓

Alert Manager

↓

Correlation Engine

↓

Alert Storage

↓

Power BI
```

Each component has a specific responsibility, allowing the architecture to remain loosely coupled and easily extensible.

# 4. Detection Rules

The system currently implements three primary detection rules.

---

## 4.1 Brute Force Detection

### Objective

Detect multiple failed authentication attempts against the same account originating from the same IP address within a defined time window.

### Detection Logic

The rule queries the recent event history associated with the user and IP address.

If the number of `LOGIN_FAILED` events exceeds the configured threshold, an alert is generated.

### Configuration

* Threshold: 5 attempts.
* Time Window: 5 minutes.

### Generated Alert

```text
BRUTE_FORCE_ATTEMPT
```

---

## 4.2 Resource Enumeration Detection

### Objective

Detect users attempting to access an unusually high number of different resources within a short period of time.

This behavior is commonly associated with reconnaissance activities performed before a more sophisticated attack.

### Detection Logic

The rule counts the number of unique resources accessed by a user.

When the number exceeds the configured threshold, an alert is generated.

### Configuration

* Threshold: 10 unique resources.
* Time Window: 15 minutes.

### Generated Alert

```text
RESOURCE_ENUMERATION
```

---

## 4.3 Credential Stuffing Detection

### Objective

Detect failed authentication attempts against multiple user accounts originating from the same IP address.

This pattern typically indicates the use of credentials previously leaked from other platforms.

### Detection Logic

The rule identifies how many different users have generated `LOGIN_FAILED` events from the same IP address.

When the number exceeds the configured threshold, the system generates an alert.

### Configuration

* Threshold: 5 users.
* Time Window: 10 minutes.

### Generated Alert

```text
CREDENTIAL_STUFFING
```

---

# 5. Alert Suppression

Continuously generating similar events can produce a large number of identical alerts, making analysis more difficult for the security analyst.

To address this issue, Cloud Security Lab incorporates an alert suppression mechanism.

Before storing a new alert, the system verifies whether an equivalent alert already exists for the same IP address within a configurable cooldown period.

If a recent alert is found, the new alert is discarded.

### Objective

Reduce operational noise and prevent unnecessary alert duplication.

### Configuration

Cooldown: 5 minutes.

---

# 6. Correlation Engine

The detection of a single rule does not necessarily represent a complete attack.

For this reason, the system includes a Correlation Engine responsible for analyzing previously generated alerts.

When the same IP address simultaneously exhibits the following behaviors:

* Brute Force
* Resource Enumeration
* Credential Stuffing

the system determines that there is sufficient evidence to classify the activity as a multi-stage attack.

As a result, it generates a higher-level alert.

### Generated Alert

```text
MULTI_STAGE_ATTACK
```

This approach provides a simplified representation of the correlation mechanisms commonly used by enterprise SIEM platforms.

---

# 7. Detection Pipeline Integration

The Detection Pipeline coordinates the operation of all system components.

For every incoming event, it performs the following operations:

1. Execute the Detection Engine.
2. Process each alert through the Alert Manager.
3. Store only alerts that are not suppressed.
4. Execute the Correlation Engine.
5. Process the correlated alert through the Alert Manager.
6. Store the correlated alert when applicable.
7. Return all valid alerts for visualization.

This workflow ensures that only relevant alerts reach the analysis layer.

---

# 8. Current Limitations

Version 1.0 implements only a subset of detection techniques.

The following capabilities are not currently implemented:

* Password Spraying Detection.
* Impossible Travel Detection.
* Lateral Movement Detection.
* Privilege Escalation Detection.
* Data Exfiltration Detection.
* User and Entity Behavior Analytics (UEBA).
* Machine Learning.
* Anomaly Detection.
* Threat Intelligence Integration.

These capabilities are planned as part of the project's future roadmap.

---

# 9. Future Evolution

The Detection Engine was designed with a modular architecture that allows new detection rules to be incorporated without modifying the existing ones.

Future versions aim to extend the engine by incorporating:

* New behavior-based detectors.
* Advanced correlation.
* Risk Scoring.
* MITRE ATT&CK integration.
* Machine Learning-based detection.
* SOAR platform integration.

The current architecture provides a solid foundation for evolving from an academic laboratory into a security analysis platform significantly closer to those used in the cybersecurity industry.
